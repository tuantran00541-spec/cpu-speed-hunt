# CPU inference speedup hunt — research verification

- **Date:** 2026-11-21
- **Model:** base `huihui-ai/Huihui-Qwen3.5-0.8B-abliterated` (derivative of `Qwen/Qwen3.5-0.8B`; ~0.8B LM + vision encoder, safetensors only, no GGUF in the source repo). Task: image in → Vietnamese text out, prompt "Dịch chữ trong ảnh sang tiếng Việt.", greedy, `max_new_tokens=100`.
- **Target HW:** free GitHub Actions `ubuntu-latest` (4 vCPU, ~16 GB RAM); later the user's Windows laptop CPU.
- **Method:** every claim below was checked against an official doc page, repo README, or source file. Second-hand/blog claims are labelled as such and never used as the sole basis for a "supported" verdict.
- **Scope note:** "supported" here means *the runtime documents this model/arch + vision path*. It does NOT mean "fast on 4 vCPU" — that is what the bench phase measures.

## 2. Model facts (grounding)

- `Qwen/Qwen3.5-0.8B`: "Type: Causal Language Model with Vision Encoder", 0.8B LM, hidden 1024, 24 layers, "Hidden Layout: 6 × (3 × (Gated DeltaNet → FFN) → 1 × (Gated Attention → FFN))", "MTP: trained with multi-steps", "Context Length: 262,144 natively", "Qwen3.5-0.8B operates in non-thinking mode by default". <https://huggingface.co/unsloth/Qwen3.5-0.8B-GGUF> (mirrors the Qwen card).
- `huihui-ai/Huihui-Qwen3.5-0.8B-abliterated` is an abliterated derivative of `Qwen/Qwen3.5-0.8B` (full multimodal model incl. vision encoder + adapter; "both text and image inputs are supported" — per the sibling `g-ntovas` card describing the same base; the huihui card itself lists the base as `Qwen/Qwen3.5-0.8B`).
- Consequence for the hunt: this is a **hybrid SSM (Gated DeltaNet) + full-attention** model, not a pure-attention transformer. Anything that assumes pure attention (KV-cache shifting, some prefix-caching, some speculative decoding) may behave differently — see §3.

## 3. Combo pieces — stacking INSIDE one runtime only

### 3.1 llama.cpp (single runtime: GGUF + mtmd)

| Piece | Flag / setting | Status + source |
|---|---|---|
| Threads | `-t N` / `--threads N` (prompt+decode), `-tb N` / `--threads-batch N` (batch/prompt processing) | Standard llama.cpp flags. On 4 vCPU: `-t 4 -tb 4`. |
| Flash attention | `-fa on` / `--flash-attn on` | Documented; axteam card: "the commands on this card use `-fa on` (≥ b6325)". |
| KV-cache type | `--cache-type-k q8_0 --cache-type-v q8_0` | Documented; "halves the KV cache" (axteam card). |
| Prompt cache (server) | `--cache-prompt` (default on), `--cache-ram <MiB>` (default 8192) | Server README via secondary docs: "`cache_prompt` defaults to `true`". Our workload is 3 different images with an identical short prompt — prefix reuse across *different* images is ~nil (image tokens differ), so prompt-cache gains here are limited to the repeated text suffix, if any. |
| Cache reuse (KV shifting) | `--cache-reuse N` (e.g. 256) | **Do NOT stack for this model.** llama.cpp's own server log (quoted in an independent write-up): "`cache_reuse is not supported by multimodal, it will be disabled`". Reason: Qwen3.5's SSM (Gated DeltaNet) state "can only return to a point that was saved" — it cannot be KV-shifted. Treat `--cache-reuse` as disabled-by-the-runtime for Qwen3.5 VL; verify from the server log in the bench run (OPEN O1). |
| Speculative decoding — MTP | `-md <mtp-sidecar.gguf> --spec-type draft-mtp --spec-draft-n-max N` | Supported in principle: unsloth ships `unsloth/Qwen3.5-0.8B-MTP-GGUF` with the note "MTP speculative decoding for ~1.5-2x faster generation … llama.cpp renamed `--spec-type mtp` to `--spec-type draft-mtp` on 2026-05-13", example: `llama-server -hf unsloth/Qwen3.5-0.8B-MTP-GGUF:UD-Q4_K_XL -ngl 99 -c 8192 -fa on -np 1 --spec-type draft-mtp --spec-draft-n-max 6`. **Critical blocker for our task: the same card states "`-np > 1` and `--mmproj` are not yet supported with MTP."** So MTP speculative decoding and vision (`--mmproj`) cannot be combined in llama.cpp today. For image→text, MTP is therefore NOT stackable; it is text-only. A separate small draft model (`-md <small.gguf> --spec-type draft`, classic draft) is the alternative, but no suitable Qwen3.5 draft pair was verified — OPEN O7. |
| Speculative decoding — prompt lookup / N-gram | `--spec-type prompt-lookup` (llama.cpp `docs/speculative.md` lists implementations incl. draft, draft-eagle3, draft-mtp) | Exists in llama.cpp, but for translation output (which does not copy the prompt) acceptance will be near zero. Not recommended for this task. |
| Recommended llama.cpp stack for the bench | `llama-mtmd-cli -m <Q4_K_M.gguf> --mmproj <mmproj-F16.gguf> -t 4 -tb 4 -fa on --cache-type-k q8_0 --cache-type-v q8_0 -c 2048 --image <img> -p "…" -n 100 --temp 0` | Text quant Q4_K_M is the usual choice; also try Q8_0 (quality) and Q5_K_M. Do NOT add `--cache-reuse` or `--spec-type draft-mtp` with `--mmproj` (see above). |

### 3.2 OpenVINO GenAI (single runtime: OV IR + GenAI)

| Piece | Setting | Status + source |
|---|---|---|
| Threads | OpenVINO Runtime CPU property `ov::inference_num_threads` / `INFERENCE_NUM_THREADS` (e.g. `core.set_property("CPU", {"INFERENCE_NUM_THREADS": "4", "NUM_STREAMS": "1"})`) | Documented for OpenVINO Runtime (`optimum.intel` models accept an `ov_core`). Whether `openvino_genai` `VLMPipeline`/`LLMPipeline` accepts device properties directly was **not verified** — OPEN O3. Workaround in bench: set `OMP_NUM_THREADS=4` / pass properties if the GenAI constructor accepts them; record what the pipeline actually used. |
| Prefix caching | `SchedulerConfig.enable_prefix_caching` (default on when no `SchedulerConfig` passed) | Documented (GenAI spec-decoding doc, §2d). With hybrid-attention models (Qwen3.5): "reuse also depends on linear-attention state checkpoints" and "speculative decoding of hybrid-attention models supports greedy decoding only" with prefix caching. Our task is greedy, so ON is fine for the non-spec path. |
| MTP speculative decoding | `draft_model(model_path, "CPU")` + `VLMPipeline(…, draft_model=draft, scheduler_config=…)` with `enable_prefix_caching=False` | Supported per §2d, **only if the export emits `openvino_mtp_model.xml`** (check the export dir; if absent, MTP is unavailable and this combo drops). Greedy-only, prefix-caching OFF. |
| Other spec strategies on VLMPipeline | Prompt Lookup (`prompt_lookup=True` at construction), EAGLE3, DFlash, DSpark | Documented as supported on `VLMPipeline`. No EAGLE3/DFlash draft exists for Qwen3.5-0.8B (DFlash list is `Qwen3.5-*-DFlash` — family-level, no 0.8B artifact verified) — OPEN O8. Prompt Lookup is free (no draft model) but near-useless for translation output. |
| Weight format | INT4 vs INT8 export (`--weight-format int4` / `int8`) | Both documented; INT4 is the aggressive option, INT8 the safer one. Bench both. |
| Recommended OpenVINO stack for the bench | Export INT4 + INT8 → `OVModelForVisualCausalLM` (simple path) AND `VLMPipeline` (GenAI path) → GenAI + MTP if `openvino_mtp_model.xml` present (greedy, prefix-caching off) → GenAI plain with prefix caching on (no spec) as the control. | Keep the two OpenVINO APIs separate in results: optimum-intel `generate()` vs GenAI `VLMPipeline.generate()` are different code paths. |

### 3.3 PyTorch CPU (single runtime: transformers + torch)

| Piece | Setting | Compatibility verdict |
|---|---|---|
| `torch.compile` | `torch.compile(model, mode="default")` / `"max-autotune"` (+ `TORCHINDUCTOR_FREEZING=1`, `torch.no_grad()`) | Baseline supported; expect graph breaks on the VL `generate()` loop and long first-call compile on 4 vCPU. |
| IPEX `optimize` | `ipex.optimize(model, dtype=torch.bfloat16)` / `ipex.llm.optimize(...)` | Standalone API, documented. No VL-specific evidence. |
| IPEX + `torch.compile` | `ipex.optimize(model, weights_prepack=False)` then `torch.compile(model, backend="ipex")` | **This is the documented combination** (IPEX docs, TorchDynamo mode). Stackable. |
| INT8 (TorchAO) | `TorchAoConfig(quant_type=Int8WeightOnlyConfig())` at `from_pretrained` | Documented for VL models (Qwen2.5-VL precedent). |
| INT8 + `torch.compile` / IPEX | All three together | **Unproven.** No source documents TorchAO INT8 weight-only + IPEX optimize + `torch.compile` stacked on one VL model. Bench pairwise first (TorchAO alone; IPEX+compile; TorchAO+compile), and only then the triple — record any error / slowdown. Do not report the triple as "supported" without a passing bench run. |
| Threads | `torch.set_num_threads(4)`, `OMP_NUM_THREADS=4` | Standard. |

### 3.4 Cross-runtime stacking — NOT allowed

Do not combine e.g. llama.cpp GGUF + OpenVINO, or vLLM + llama.cpp draft, in one bench configuration. Each bench run uses exactly one runtime's own stack above.

## 4. Bench shortlist (from this verification)

1. **llama.cpp GGUF + mmproj** (Q4_K_M, also Q8_0) — strongest documented VL path on CPU; expected baseline winner.
2. **OpenVINO optimum-intel `OVModelForVisualCausalLM`** INT8 and INT4 — strongest documented alternative; plus GenAI `VLMPipeline` (plain, prefix caching on) and GenAI + MTP if the export emits the MTP file.
3. **PyTorch baseline** (BF16, `torch.compile mode="default"`) and **TorchAO INT8 weight-only** — baseline/reference only; IPEX variants as stretch.
4. **Do NOT bench as primary candidates:** vLLM GGUF (unsupported), vLLM CPU HF-weights (unproven — one smoke attempt max), SGLang CPU (AMX requirement + no Qwen3.5-VL listing — one smoke attempt max, only if the runner reports AMX), ONNX Runtime via optimum (no VL class — one export smoke attempt max), ncnn / MNN (no usable documented path for this model on Linux CPU).

## 5. OPEN items (could not be verified — bench phase must resolve)

- **O1 — llama.cpp `--mmproj` conversion for Qwen3.5 specifically.** The `--mmproj` converter flow is documented for Qwen2/2.5-VL; Qwen3.5 mmproj existence is proven only by the unsloth artifact (`mmproj-F16.gguf` in `unsloth/Qwen3.5-0.8B-GGUF`). Bench must run `convert_hf_to_gguf.py --mmproj` on the huihui checkpoint and confirm it succeeds and `llama-mtmd-cli` reads an image. Also confirm from the server log whether `--cache-reuse` is disabled for multimodal/Qwen3.5.
- **O2 — optimum-intel export task flag for Qwen3.5 VL.** Whether `--task image-text-to-text` is accepted for `huihui-ai/Huihui-Qwen3.5-0.8B-abliterated`, or whether the export must be run without `--task` (as in the Qwen2.5-VL Lenovo guide). Also whether the export emits `openvino_mtp_model.xml` for the 0.8B model (needed for the GenAI MTP combo).
- **O3 — OpenVINO GenAI thread control.** How to set CPU thread count on `VLMPipeline`/`LLMPipeline` (device properties vs env vars). `ov::inference_num_threads` is documented for OpenVINO Runtime, not verified for the GenAI pipeline constructors.
- **O4 — vLLM CPU + Qwen3.5 VL + transformers version skew.** Whether current vLLM (CPU wheel) accepts `transformers>=5` (required by Qwen3.5) and loads the HF VL checkpoint on CPU at all. One smoke attempt; if it fails on version/architecture, drop it.
- **O5 — SGLang CPU on GitHub Actions runners.** Whether the runner CPU exposes Intel AMX (required by the official CPU Servers doc). Check `lscpu` / `/proc/cpuinfo` for `amx-*` flags; if absent, SGLang CPU is definitively out on this hardware.
- **O6 — ncnn / MNN usable paths.** `futz12/ncnn_llm` claims Qwen3.5 VL support and MNN-LLM v0.8.3 claims Qwen3.5 support, but neither yielded a verified Qwen3.5-0.8B artifact, converter command, or Linux-CPU run for this model. Do not spend bench time unless O1–O5 leave no viable candidate.
- **O7 — llama.cpp classic draft model for Qwen3.5.** No small Qwen3.5 draft pair was verified; MTP + `--mmproj` is explicitly unsupported per unsloth. Classic `--spec-type draft` with a separate draft GGUF remains unproven for this model.
- **O8 — EAGLE3 / DFlash drafts for Qwen3.5-0.8B.** Optimum-intel lists `Qwen3.5-*-DFlash` at family level and EAGLE3 draft support in 2.0, but no 0.8B draft artifact was found. Do not assume availability.
- **O9 — TorchAO INT8 + IPEX + torch.compile triple stack.** No source documents all three together on a VL model (see §3.3). Bench pairwise first.
- **O10 — `ggml-org/Qwen3.5-0.8B-Base-GGUF` mmproj contents.** The repo page crawl did not expose its file list; whether the official auto-converted repo ships an mmproj was not confirmed. Reference only — does not affect the bench (we convert the huihui base ourselves).
